## 获批补强执行包

1. **先使诊断成本可见。** 对正常高频事件按短窗口汇总次数、总耗时、最大耗时与结果类别；慢操作、异常、超时、取消、状态变化及恢复保留单独记录。活动中的阶段继续可被观察，不等操作返回才发现它卡住。诊断记录失败与队列溢出分别计数，不再用一个零丢失数字代表完整性。
2. **补齐具体等待边界。** 沿用现有请求／任务关联，增加结果消费、对象组装、媒体响应和任务调度结果；明确“执行 SQL 完成”和“数据库结果已读取完成”的区别。对内部动作只观测，不改优先级、并行数、缓存、检查范围或超时。
3. **接上浏览器证据。** 增加仅诊断构建启用的事件接收入口和请求关联响应头；浏览器短批上报，有界缓冲、固定字段及体积限制。只记录类别、数量、时长和随机关联标识，不发作品内容、搜索词、请求正文、凭据或完整 URL；诊断上报失败不触发业务重试，不递归记录自身。前后台切换、加载失败与取消也要记录，Chrome 不提供的指标明确缺失，不猜测。
4. **保持持续记录。** 继续约 64 MiB 分卷、逐条时间戳和跨卷关联，没有累计容量停录。上报或磁盘写入失败可见，已有卷原样保留；正常路径汇总不等于截断异常日志。线程栈不含局部变量。恢复事件补上重启前后可对应的任务关联，不为诊断新增业务数据库字段。
5. **只验证取证本身后交日常使用。** 做一次小型合成验证，覆盖前后端关联、慢结果消费、超时后的实际清理、分卷、上报失败及诊断不覆盖原业务异常；同一小负载比较探针开关的时间与日志量，记录数值，不把它外推为真实图库性能。最终 EXE 核对正常启动、已有登录／自动检查方式、日志生成和退出后交用户试用，不跑全量或长测。

实现依赖现有 Python／FastAPI／Vue 与已安装依赖，不引入新的监控服务、数据库或线上平台。保持公开版本 `0.2.0`，实施时使用新的内部构建号，业务基线和诊断改动分开登记。

## 日常观察与交接方式

- 用户照常使用；遇到异常时给大致时间和刚做的动作即可。证据应尽量由程序自己保留，不要求用户为每次问题手工操作开发者工具。
- 以当前内部构建作为固定观察基线。新增问题先登记，不自动转成修复任务；确需恢复可用性的操作另在本会话决定。
- 只比较日志确实覆盖的场景，例如空闲／自动检查／用户主动维护／连续看图／前后台切换／退出。未发生的场景标未观察，不人为制造大规模真实账号任务。
- 每次故障保留前后相邻日志卷、运行／构建标识、请求和任务关联、取消后的状态；没有完整链路就保留“待查”，不把相关性写成因果。
- 本轮没有建立定时自动检查或跨会话消息。后续分析由本会话结合用户反馈进行；独立重写通过报告接收经验，旧业务继续暂停修补。
