- **问题：** 用户反馈日志无法加载，多个入口反复出现 `signal timed out`，要求核实是否存在架构问题。
- **基线：** `main / 6caefe6`，日常 `0.2.0 · 20261004.2`；本轮未修改应用源码、运行包、配置、令牌或数据库结构，未新建真实账号任务。
- **结论：** 已确认日志查询成本、前端请求生命周期、后端读取收尾存在缺口；收藏锁与连接的相反获取顺序在隔离条件下可触发等待，正式装配还遗漏了任务客户端上下文。此前局部查询优化有效，但没有构成完整的故障隔离与日常验收，BUG-103 继续开放，新增 BUG-105／106。
- **状态：** 诊断与隔离候选；不是修复交付。真实旧任务是否全部完成、所有历史超时是否同一原因，本次没有下结论。

## 已确认的缺陷

### 1. 日志只限制返回数量，没有限制查询工作量

[activity_log.py](../../app/src/core/activity_log.py) 的日志入口只展示最近最多 100 个操作、200 条失败明细，但复合 `OR` 条件使本次查询计划仅按操作 ID 查找，再检查该任务的大量步骤并排序。完整 ORM 记录还带出日志不用的 `target`、`depends_on`、任务 `parameters` 等字段。

这不是 Python 一次加载十五万个对象：实际返回行数很少，昂贵工作发生在数据库筛选和排序阶段。宽字段浪费与状态扫描是两个问题，仅缩小字段不能消除扫描。

在纯内存 SQLite 中调用现行函数，与“拆分互斥状态分支＋只读必要字段”的隔离候选比较，输出完全相同：

| 合成输入 | 现行数据库指令步数 | 候选步数 | 说明 |
| --- | ---: | ---: | --- |
| 现有 150,512 步维护夹具 | 1,222,100 | 14,200～14,300 | 工作量约为原来的 1/86；未修改索引 |
| 10,000 步、10 条失败、每条目标资料 2 KB | 80,400～80,500 | 400 | 返回文本字段由约 87.6 KB 降至 742 字节 |
| 10,000 步全部失败 | 293,500 | 172,500～172,600 | 仍需读取大量失败，不是固定成本 |
| 10,000 步全部跳过 | 130,000～130,100 | 80,100 | 仍需筛选跳过原因，不是固定成本 |

候选复用了已有状态索引，不需要改表或新索引。现有 3 条日志合同绑定候选后通过，保留脱敏、原因、顺序、空库、数量和截断语义。内存耗时不能外推为真实机械盘或最终 EXE 的提速倍数；全失败和全跳过反例也说明局部查询修复不能代替读取保护。

详见[查询汇总](证据/2026-10-04-日志超时与读写边界复审/log-cost-summary.json)、[候选合同](证据/2026-10-04-日志超时与读写边界复审/candidate-semantics-result.json)。

### 2. 同一读取可以重叠，旧响应可以覆盖新结果

[SettingsView.vue](../../app/frontend/src/views/SettingsView.vue) 的日志收放只检查是否已有结果，不检查正在读取；收起、离页没有取消日志请求，也没有拒绝旧响应。提取现行组件脚本并替换界面／HTTP 环境后，快速打开→收起→打开稳定产生两个 GET；新请求完成后加载标记提前消失，旧响应仍可覆盖新结果。设置读取也有同类竞争。

这项结果证明实际脚本的生命周期缺陷，不冒充真实 Vue 页面、EXE 或手机验收。图库和来源一览已有 `LatestIntent`，任务进度轮询也有在途门禁及离页取消，不能把局部缺口扩写成所有页面都会堆请求。

证据：[前端复现](证据/2026-10-04-日志超时与读写边界复审/frontend-boundary-result.json)。

### 3. 超时只结束页面等待，没有贯通到数据库读取

[api.ts](../../app/frontend/src/api.ts) 为每次调用设置 30 秒总预算，但直接抛出原生超时异常；设置和日志直接显示其 `message`。独立 Chromium 空白页实测该原生文案就是 `signal timed out`。它表示前端等待超时，不包含实际卡在哪里的信息，不能据此判断 Pixiv 限流或网络故障。

后端日志是同步路由，由线程执行；[database.py](../../app/src/core/database.py) 只有锁等待设置，没有运行中只读 SQL 的执行预算、客户端断开收尾或昂贵查询去重。[AnyIO 官方说明](https://anyio.readthedocs.io/en/stable/threads.html#running-a-function-in-a-worker-thread)也明确：取消等待不自动终止工作线程，丢弃结果也不等于停止执行。

补保护时必须区分读取和写入：安全中止过期读取，不取消已经提交的收藏、下载记录或原子发布；客户端超时的写操作仍需回读，不能自动重放。SQLite 提供[查询中断与进度回调](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.set_progress_handler)，但它们不保证立即打断任意操作系统磁盘等待，仍需短查询和有限并发。连接归还前清除取消钩子，避免迟到取消误伤下一请求。

受控实验证明后端边界缺口：使用实际设置路由、真实 HTTP 和随机本机端口，将日志读取换成最多等待 1.5 秒的替身；客户端在 150 毫秒超时断开，服务端已收到 `http.disconnect`，读取函数仍活动，直到实验主动释放。服务器正常退出，无数据库或账号操作。它证明同步入口不会自动停止，不声称已关联真实库中某条 SQL 的请求身份。

证据：[浏览器原生文案](证据/2026-10-04-日志超时与读写边界复审/chromium-native-timeout-result.json)、[实际路由断开实验](证据/2026-10-04-日志超时与读写边界复审/server-disconnect-result.json)。

### 4. 收藏锁与数据库连接存在相反的获取顺序

[bookmarks.py](../../app/src/core/bookmarks.py) 的 `apply_observation()` 持收藏锁等待数据库写入；[library.py](../../app/src/core/library.py) 则在仍持读连接时等收藏快照的同一把锁。连接资源紧张时可以互相阻挡。

两线程、纯内存、刻意缩为 1 个连接、0.25 秒连接等待的可终止实验：现行顺序使写者 `TimeoutError`；读者先归还连接再取快照的对照成功，两个实验最终均无残余线程或占用连接。此结果证明一种可触发缺陷，不能认定日常默认连接池此刻已经发生同样的锁环。

修订必须保留收藏账号绑定、版本比较、请求去重和提交后才更新可信缓存，不能直接删锁求快。证据：[锁顺序对照](证据/2026-10-04-日志超时与读写边界复审/lock-order-result.json)。

### 5. 正式运行中的远端代理没有接到任务上下文

[runtime.py](../../app/src/core/runtime.py) 实际将 `RemoteAccess` 代理交给任务处理器，但 [tasks.py](../../app/src/core/tasks.py) 从代理的类上查找 `task_scope`；代理仅能转发实例属性，类上没有该方法。因此 [client.py](../../app/src/client.py) 原定的任务内单次请求、按任务检查暂停的上下文未生效。

无网络替身对照：正式代理路径触发 3 次连接尝试、任务检查点 0 次；直接客户端路径仅尝试 1 次、任务检查点 2 次。等待由替身记录而未实际执行。该缺陷会延长维护单步骤并削弱请求边界让出／暂停；它不是本地日志查询阻塞的直接原因，也不等于所有暂停与重试机制都失效。

登记 BUG-106；修订应给正式适配层明确协议并使用实际装配回归，保留账号重新连接、持久重试与退出行为。证据：[无网络生产装配对照](证据/2026-10-04-日志超时与读写边界复审/remote-scope-result.json)。

## 架构判断与尚未证实的部分

前台浏览、辅助日志与后台维护共用数据库及执行资源，这本身可行，但当前没有把查询成本、资源受理和取消收尾作为统一约束；恢复用的明细记录又被部分界面直接反复筛选，历史增长后成本暴露出来。局部索引和分页只能减少某些查询的工作，不能保证一个遗漏的慢接口不会继续占资源。

长读事务可能延迟 WAL 检查点，这是 [SQLite 官方文档](https://www.sqlite.org/wal.html#concurrency)描述的机制；本次看到 WAL 文件和提交等待，尚不足以证明检查点是这轮停顿的直接根因。也未证明磁盘故障、永久死锁、真实连接池已经耗尽或现有存档损坏。

继续保留现有 SQLite、单写事务、WAL 一致性、文件发布与恢复记录。当前证据支持收敛读写边界，没有证明更换数据库或全部重写能得到更优结果。

## 验证为什么漏掉

- 现有日志测试只有 3 个失败步骤、110 个空任务、1 个跳过项，验证了输出内容与数量，没有验证扫描成本。
- 本次前端 API／交互 22 项仍通过；其中超时用例要求 `TimeoutError` 类型，没有检查产品中文反馈或设置页的重叠／离页行为。
- 上一轮 40 并发包含图库、设置和进度，但漏了日志，后台处理器又是本地读取替身，没有覆盖真实来源保存、收藏确认及持久提交之间的组合。
- 直接客户端通过的任务上下文测试，没有覆盖正式 `Runtime → RemoteAccess → Handler → PixivClient` 装配路径，导致适配层约定落空。
- 上一轮已注明长期使用未验收，但必要日常路径仍未覆盖，不能把缺口交给用户日常使用来兜底。
