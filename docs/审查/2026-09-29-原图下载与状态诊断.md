# 抓到新作但没有原图：下载与状态诊断

2026-09-29；源码基线 `main` / `9bed0ba`，0.2.0 构建 20260929.2。状态：已诊断，未修复；未重试真实下载或操作账号。

## 现场结果

通过正在运行的本地服务只读查询最近一次“检查新作品”：任务 `738d30d187a341f8ac7277051f5cbff1` 于 2026-09-29 16:58:56（北京时间）结束，结果为失败。

- 30 项原件下载全部失败，记录为“图片来源拒绝访问，请检查登录状态后重试”；13 项缩略图因前置步骤失败未执行。
- 查询时没有活动任务和排队任务，因此这批原件不是仍在等待下载。
- 前 30 张图库卡片中有 13 张返回 `preview_status=pending`，与任务失败提示不一致。
- 当前下载器将 HTTP 401、403 归为同一拒绝提示；任务记录未保留具体状态码。仅凭现有记录不能判断是登录、来源地址还是请求环境问题，也不能断言重新登录可解决。

## 实现原因

新作品的信息先由 `_save_remote_work` 保存，原图之后由下载任务获取。信息获取成功并不代表图片已存档。

下载拒绝后，资产正确记为 `failed` 并保留原因。但后续缩略图清点调用 `_inspect_asset`，发现没有本地路径又改写成 `missing`，错误也被“缺少原件”覆盖。图库据此返回 `pending`，前端显示“原图尚未下载”。这是 BUG-071，不是页面缓存。

合成一件作品，以替身下载器返回拒绝错误，经真实 `TaskQueue` 执行补下载、再执行缩略图清点；无需联网。结果从 `failed / 原图下载失败` 变为 `missing / 原图尚未下载`，原下载任务仍是失败，见[隔离结果](证据/2026-09-29-原图下载与状态诊断/status-overwrite.json)。本轮没有修改实现。

## 修复边界

- 原图为何被图片来源拒绝仍待定位，不能以调整占位文字代替下载修复。
- 文件是否存在与最近一次下载是否失败分别表达，清点和缩略图任务不抹去下载失败事实。
- 验收覆盖下载失败后生成缩略图、再次检查、重启与重试；失败卡片明确显示失败，成功补齐后才转为可用。

前一修订包验证了卡片的各个输入状态，未覆盖“下载失败后再清点缩略图”的连续流程，因此不能据其测试通过认定这一问题已解决。

## Pixiv 批量请求限制调查

用户补充旧 AI 曾提及 Pixiv API 限制。以下区分外部一手资料、本项目实现和未确认的原因；资料核查日期为 2026-09-29。

### 有依据的限制

- **接口限流确实存在。** gallery-dl 维护者的[问题记录](https://github.com/mikf/gallery-dl/issues/535)区分了 HTTP 429 与 JSON 正文的 `Rate Limit`。本次读取的[现行 Pixiv 接口代码](https://github.com/mikf/gallery-dl/blob/master/gallery_dl/extractor/pixiv.py#L1194-L1220)仍单独处理正文限流，等待 300 秒后重试；这是工具的处理策略，不是 Pixiv 保证五分钟解限。
- **接口请求间隔、下载间隔和传输速度是不同限制。** [gallery-dl 配置说明](https://gdl-org.github.io/docs/configuration.html#extractor-sleep-request)将数据提取请求间隔与每次图片下载前的等待分别配置。仅给图片限速，不能减少重复查询作品列表、资料和收藏的请求。
- **没有查到可当保证使用的官方数值配额。** 核查 Pixiv 帮助中心和相关检索，未找到当前 App API 各接口稳定公开的每秒／每天额度。旧项目的“1 req/s 安全基线”是工程取值，不是官方保证；[PixivPy 维护者的讨论](https://github.com/upbit/pixivpy/issues/344)也没有给出确定配额。
- **分页上限需按接口判断。** 搜索接口存在 offset 5000 限制的一手报告，2026 年仍有[大规模标签搜索的边界问题](https://github.com/mikf/gallery-dl/issues/8843)。不能把它解释为整个本地图库只能存 5000 件，或未经验证便套用到画师作品列表。
- **429 可给出等待时间。** [RFC 6585 第 4 节](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)定义其含义及可选 `Retry-After`；没有 429 也不能绝对排除服务端采取其他限制，但 401／403 本身同样不能证明是限流。

### 本项目实际处理

| 范围 | 当前实现与影响 | 入口 |
| --- | --- | --- |
| 作品列表、详情、资料 | 请求 `app-api.pixiv.net`，有约 1 秒的类级节流；每位画师分别分页读取插画和漫画 | `app/src/client.py` 的 `_request`、`_throttle`、`get_all_artist_illusts` |
| 正文限流与 HTTP 限流 | 只有通过 HTTP 检查后的正文限流会进入 60／120／180 秒重试；HTTP 429 会先抛错，没有执行这套等待，也不使用其 `Retry-After` | `app/src/client.py:100-115` |
| 跨请求协调 | 正文限流重试写实例 `_last_request`，普通节流读类属性；重试也未再次通过统一节流入口，不能保证其他调用共享冷却 | `app/src/client.py:112`、`245-253` |
| 原图与画师头像 | 使用独立 Requests 会话访问图片域名；已带 Referer，但没有独立的请求间隔、429 冷却和 5xx 重试 | `app/src/core/download.py`、`app/src/core/profiles.py` |
| 当前下载并行度 | 原件任务逐项执行，不能从 30 次失败推出程序并发打爆服务 | `app/src/core/tasks.py:288-319` |
| 收藏 | 有独立的 429 冷却与写入后回读，不能把这部分保障推定为所有 API 和下载均已覆盖 | `app/src/client.py:215-233`、`app/src/core/bookmarks.py` |
| 错误证据 | 下载的 401／403 合并为检查登录提示，任务只保留异常类名和文字，丢失精确状态码及服务端等待要求 | `app/src/core/download.py:46-49`、`app/src/core/tasks.py:52-55` |

API 成功与图片失败可以同时发生：两者是不同端点、不同请求流程。头像和原图有同类拒绝记录，说明需要检查共用图片请求路径；尚不足以断言是 User-Agent、代理或来源地址导致。图片请求不带 API Bearer 本身不构成缺陷，不应将账号凭据盲目转发到图片域名。PixivPy 的[下载实现](https://github.com/upbit/pixivpy/blob/master/pixivpy3/api.py#L180-L202)也单独传入图片 Referer。

### 隔离验证：BUG-072

从当前 `client.py` 提取原有类与响应检查函数，用假响应、假时钟及空鉴权函数运行；不导入项目配置、不访问账号或网络。主会话审阅并复跑[验证脚本](证据/2026-09-29-原图下载与状态诊断/rate-limit-probe.py)，[结果](证据/2026-09-29-原图下载与状态诊断/rate-limit-result.json)如下。

| 模拟响应 | 实际请求次数 | 模拟等待 | 观察 |
| --- | ---: | --- | --- |
| HTTP 429，正文 Rate Limit | 1 | 无 | 直接抛出 429，未进入冷却／重试 |
| HTTP 200，正文 Rate Limit | 4 | 60、120、180 秒 | 原请求加三次重试，持续限流后结束 |
| HTTP 403 | 1 | 无 | 直接抛出 403，不会被识别为正文限流 |
| 正文限流重试后立即发起下一请求 | 1 | 无额外间隔 | 类级节流时间未随重试更新，下一请求与上次重试的假时间相同 |

这些结果确认程序的限流处理缺口，不证明真实失败任务曾触发 429。网络返回何种拒绝仍需保留精确证据再判断。

### 处理建议与调查边界

1. 先保留精确、脱敏的响应状态、请求类别、目标主机和必要等待信息，区分登录、访问拒绝、限流、网络失败；不得输出令牌或完整响应中的敏感内容。
2. API 与图片请求分别限速、统一管理同类请求的冷却；429 和正文 `Rate Limit` 都识别，优先尊重服务端等待要求。收藏写入仍保留原有先回读、避免盲目重放的约束。
3. 日常检查减少重复资料请求，与本地全量核验分开；任务可以分开执行，但不能各自放开向 Pixiv 请求的速度。
4. 用具体获准的一件原图对照 API 与图片链路，才能继续确定这次 401／403 的来源；不因调查限制而重跑整批下载。
5. 冷却期间明确显示“等待恢复”，下载失败显示原因和重试入口；本地浏览继续可用，缩略图任务不能覆盖下载结果。
