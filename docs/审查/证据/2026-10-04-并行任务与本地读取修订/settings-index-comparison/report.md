# 两项设置形态索引：一次受控副本对照结果

结论：作品覆盖索引确实被选用，完整结果的逻辑读取约减 49.1%；版本覆盖索引没有被原 SQL 选用，所以它的收益尚未证明。12 次完成结果相同，另外 12 次按原预算取消，本轮不能宣布四臂完整等价或长期验收通过，也不能凭版本单项组的快速完成决定保留第二条索引。未追加查询、重跑、ANALYZE 或查询改写。

## 固定输入与退出

- 基线 a21c86e，统计 SQL/参数完全沿用上一轮 baseline；生产源码、现有测试、配置和真实图库未改。测量不导入 ArchiveDatabase/Runtime。
- 原始 08 合成库 605646848 字节，runtime_closed=true、无非空 WAL；只以文件只读方式打开它作复制，未作为写连接打开。四份目标均实际流式回读 SHA-256，与各自源流及彼此一致：`b00a418a6bba973fbd30cf6ce083edc7fc6ce7a1d61a4b94b2cc174c17a4cdc1`。结束后原库 size/mtime 均未变。
- 无新增索引、仅作品索引、仅版本索引、两项索引四份副本；建索引后正常关闭/整理，确认无 WAL，再以 ro&immutable=1、query_only 读取，默认 cache_size=-2000 不变。
- 20 个子进程均由父进程 wait 得到 exit=0，runner 自身 exit=0；查询每次有 4.5 秒进度取消及父进程 10 秒硬截止，未触发进程硬超时。逐子记录和日志保留在 run-01/，退出复核见 run-01/process-exits-02.json，原子进程仍活动列表为空。
- 首次 PID 简单快照 process-exits-01.json 曾看到一个已 wait 退出的 PID 再次活动；PID 可复用，不能将其认作原子进程仍运行。第二份退出复核同时记录 wait 结果及进程创建时间/记录时间判据，复核时 20 个原 PID 均不存在。
- 各子进程受控时长合计 158.82 秒。所有副本、过程日志、失败和结果保留，没有删除文件。

## 复制、目标回读与建索引

复制/校验在所有读取前进行，建索引还会读取宽表并预热其副本页面；不清 OS 缓存。“第一读”只指新进程/新连接首读，不代表冷盘。

| 臂 | 复制秒 | 目标回读校验秒 | 建索引秒（CPU 秒） | dbstat 占用字节 | 后续 checkpoint 秒 |
| --- | --- | --- | --- | --- | --- |
| baseline | 32.5532 | 0.7643 | 无 | 无 | 0.0001 |
| works_only | 11.1073 | 0.9957 | Works 13.2883（0.4063） | 839680 / 205 页 | 0.1047 |
| revisions_only | 12.7777 | 1.2042 | Revision 0.4038（0.0938） | 733184 / 179 页 | 0.1235 |
| both | 12.4489 | 1.0153 | Works 0.2955（0.0781），Revision 0.1816（0.0781） | 合计 1572864 / 384 页 | 1.9072 |

同名索引在单项/双项副本的 dbstat 大小完全相同。原库有一页自由页，新索引会复用它：单项主库页数增加分别 204/178，双项增加 383，因此主库增长不能替代实际索引占用。页大小 4096，WAL、synchronous=2/FULL 保持。

建 Works 索引逻辑读 138309632 字节、逻辑写 852872 字节；建 Revision 索引逻辑读约 73662464 字节、逻辑写约 745752 字节（双项第二次少一个头部读取/写入，完整数值见机器结果）。双项建索引阶段加 checkpoint 共约 2.3842 秒，不包含复制/验证和此前阶段；单项 Works 的 13.3 秒与双项 Works 的 0.30 秒差异表明顺序/缓存影响很强，不能承诺真实应用只需较快的一次耗时。

## 实际执行计划

所有臂仍保留原有 MEMBER UNION、资产所属作品分组、CASE、gap、suppressed 最终过滤及其余计划结构。

| 臂 | Works 形态读取 | WorkRevision 形态读取 |
| --- | --- | --- |
| baseline | SCAN works | SEARCH work_revisions USING INDEX sqlite_autoindex_work_revisions_1 (id=?) LEFT-JOIN |
| works_only | SCAN works USING COVERING INDEX ix_works_settings_shape | 同上 |
| revisions_only | SCAN works | 同上，新增 ix_revisions_settings_shape **未被选用** |
| both | SCAN works USING COVERING INDEX ix_works_settings_shape | 同上，新增 ix_revisions_settings_shape **未被选用** |

因此版本单项组的完成不能归因于覆盖路径，建索引时对版本宽行的预热是明确混杂项。作品覆盖索引按 default_revision_id 先排序，原表扫描按 rowid；这还会改变后续非覆盖版本主键读取的访问顺序。对于 UUID 版本 ID，可能使版本宽行寻址更分散；本轮不再用额外负载确认此假设。
