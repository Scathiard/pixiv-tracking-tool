# 共享读取、写入与锁边界只读审查

- 基线：`main / 6caefe6`，公开版本 `0.2.0`，内部构建 `20261004.2`。
- 范围：网页同步执行边界、共享连接池、数据库事务、收藏锁、任务成本与故障隔离；未改应用、配置、结构、真实图库或账号，未打包。
- 本目录遵循 AGENTS.md 的 `.devtools/test-runs/` 轮次约定；脚本与证据保留，不自动清理。

## 已有线上证据，由主会话取得

- `/api/status` 约 0.011 秒返回 200，而 `/api/logs` 31 秒未取得响应；这说明数据库读取路径失效，不能概括为整个网页服务失去响应。
- 客户端结束后，原三个日志请求线程仍停在 `activity_log.py:90` 查询结果提取，后来出现第四个；后台 check 工作者的 commit 栈位置仍发生变化，因此此现场不支持“已经永久死锁”的结论。
- 线上栈来源：同级轮次 `../b20261004.2-log-diagnosis-01/runtime-after-client-timeout.txt`；本子任务未重新访问真实实例。

## 代码已确认的边界问题

- `core/database.py:57` 的唯一 engine 同时供网页、任务和收藏使用；`read():102–108` 显式持有读快照，`write():111–118` 持单写锁直到提交，缺少低优先级昂贵读取的独立受理边界。
- 本项目现有解释器内确认 SQLAlchemy 文件 SQLite 默认 QueuePool 为 5 个保留连接、10 个溢出连接、30 秒等待；Starlette 同步调用使用 AnyIO 默认 40 个线程令牌，`run_sync` 默认 `abandon_on_cancel=False`。这些是本机依赖观察，不代表已直接读取打包进程的全部配置。
- `web.py:311` 的 128 请求上限不能为本地浏览保留数据库或同步线程资源；`/api/logs` 走同一个同步路由池（`routes/settings_api.py:122–124`）。前台 30 秒终止不会主动中断 SQLite 的运行查询；应用没有数据库读取截止检查或 `interrupt` 机制。
- `activity_log.py:82–95` 限制输出数量，却不限制扫描、排序和宽记录读取成本；本轮专项另负责查询计划与最小修复。不能以响应只有 100 条判断它足够轻。
- `BookmarkService.apply_observation():393–407` 持收藏锁等待数据库写入与提交；`Library.query():288–310`、`detail():444–452` 则在持读连接期间调用 `_bookmark_view():153–156`，它经 `snapshot():161` 等待同一收藏锁。这是连接/锁相反获取顺序。
- `TaskQueue._worker():385–404` 中未被业务处理器吸收的异常会设置全队列 stop；连接资源耗尽可以使所有执行通道停下。保护性停机应保留，但必须区分“暂时等待资源”与“不安全的内部失败”。不能直接吞异常或无限重试。

## 合成已证，但未证线上触发

运行 `lock_order_probe.py`，只调用实际 `ArchiveDatabase.read/write` 和 `BookmarkService.snapshot`，不创建表或持久数据库；两线程、连接容量刻意设为 1、连接等待最多 0.25 秒。

| 条件 | 结果 | 收尾 |
| --- | --- | --- |
| 读连接→收藏锁；收藏锁→写连接 | 写者 `TimeoutError`，约 254.01ms；读者约 254.77ms | 活线程 0、占用连接 0 |
| 读者先归还连接再取收藏快照 | 写者成功，约 0.23ms；读者约 0.74ms | 活线程 0、占用连接 0 |

结果见 `lock-order-result.json`。该实验证明资源耗尽时获取顺序能够相互阻挡，不能据此说真实默认 15 连接池已经进入这个环；线上后台仍推进。对照仅验证顺序，不是正式收藏修复，也没有证明放松锁之后所有账号/版本语义等价。

## 尚未量化的风险

- 长读快照可能延迟 WAL 检查点并增加 WAL/磁盘工作；构造函数不再次修改已有库 journal mode（`database.py:94–96` 仅在新库创建时启用 WAL），本子任务没有核实真实库当前 mode、WAL 大小或检查点耗时。
- 阶段聚合虽然使用覆盖索引，仍在每步骤前后重新统计该阶段所有行（`tasks.py:757–769、819–827`），进度每次读取还执行整轮聚合（`917–943`）。索引减少每次成本，但整轮反复统计仍随清单增长；尚未证明它是本轮日志阻塞主因。
- 下载每 0.25 秒把字节展示写入数据库（`download.py:135–137` → `tasks.py:116–123`），两个下载通道会产生多次持久提交；需要量化提交占比后再决定合并纯展示进度，不能减少步骤结案与发布耐久性。
- 同步画师搜索/添加仍等远端请求（`archive_api.py` 的 search_artist/add_artist、`runtime.py:152`），请求进入网页线程池，属于另一类占用；事务作用域的直接调用扫描未发现主站网络、散列或媒体解码在数据库事务内，未证实该路径导致此次故障。

## 独立发现：生产远端适配器丢失任务上下文

- `runtime.py:85–96` 实际传入处理器的是 `RemoteAccess`，`archive.py:33` 存入 handler.client；该代理仅通过实例 `__getattr__` 转发。`tasks.py:671–672、789–791` 却在 `type(client)` 上查找 `task_scope`，所以生产代理的实际 PixivClient.task_scope 未进入。
- `remote_scope_probe.py` 用真实 RemoteAccess/PixivClient 及与 TaskQueue 相同的查找表达式验证，不创建 Runtime、不连接账号/网络；请求完全由会抛 ConnectionError 的进程内替身取代，所有等待也用记录器替代。
- 生产代理查找结果：scope 未安装，替身调用 3 次，本会等待 2/4 秒，任务 checkpoint 0 次；直接 PixivClient 查找结果：scope 安装，替身调用 1 次，无重试等待，任务 checkpoint 2 次。结果见 `remote-scope-result.json`。
- 因此任务本应“一次联网尝试后交持久队列冷却”却仍走非任务的内部连接重试（`client.py:125–144`），手动暂停也未传入该请求层任务检查（`client.py:114–120`）。暂停在其他 handler/context 检查处仍有效，不能写成完全不能暂停。
- 这是当前生产装配方式的明确代码缺陷；未测真实主站时延、没有复现这次日志查询阻塞，所以只作为独立维护边界问题，不认定为 `/api/logs` 卡住的直接根因，也不推算每步骤必然延迟多少秒。

## 应保留的机制

- 保留单写事务、WAL 一致性、独立本地浏览、图库租约、先停止工作者再关闭数据库、持久任务与有限重试、公平领取、删除意图和恢复凭据。
- `media.py:365–407` 的文件重命名留在短写事务中是发布与删除顺序的一部分；大文件散列已经移至事务外，不宜为追求绝对零磁盘调用拆掉这段正确性。
- 收藏回读确认、request_id 去重、同作品 pending 合并、账号绑定、版本比较和重启只回读必须保持；不能直接删收藏锁、丢版本校验或在提交前标记 fresh。

## 最小候选先后顺序

1. 修复实际日志查询成本，保持同一结果语义与隐私过滤；先投影必要字段、缩小有效状态/操作范围、实测计划与成本。如需新增索引，单列授权与备份，不把已有三索引授权自行扩展。
2. 建立昂贵只读请求的受理边界：日志请求至多一个在途、等价读取合并；有限查询预算在 SQLite 执行线程中生效，超预算回收连接与事务。预算是防故障扩散的兜底，不代替第 1 步，也不用于取消写入/发布。
3. 整理收藏锁顺序：内存 freshness/epoch 快照用短锁，数据库写事务不等待该锁，网页在事务外合成内存快照。去重和版本校验继续在单写事务内；提交后发布 freshness 前重新核对版本/账号，不能让较旧线程晚到覆盖新标记。
4. 补足 RemoteAccess 的显式 task_scope 协议，正确转交当前任务到实际客户端；调用方仍需保证未登录/退出边界。将“任务尝试一次、持久重试/暂停接管”放在真实 Runtime 代理装配测试，而不是只测直接客户端。
5. 若阶段统计/提交量仍是长期运行瓶颈，再改进度投影：可优先使用既有结果字段、事务内状态增量和重启校验，避免先新建表/字段。改持久聚合需覆盖多个状态转换，是跨模块计划，不适合作为日志 hotfix 顺手实施。

前两步可先无字段/迁移完成，第三步涉及 database/bookmarks/library 边界，需要主会话提出明确计划后实施；第五步才考虑更广的持久投影，当前没有更换数据库、增加线程或服务拆分的依据。

## 有限验证建议

- 用现有 15,000 件作品、150,512 步骤的合成形态，添加已完成/失败/不可获取 skipped 混合分布、多个历史操作和较宽 JSON；同时测日志实际 SQL 指令数、返回语义与总耗时。
- 重放一次客户端超时，最多四个等价日志读取，检查服务端在预算内归还线程与连接；期间本地详情/图片/设置/进度继续可读，原维护持久计数继续推进。
- 两线程锁顺序回归须在当前实现失败、候选通过；补去重、两个快速点击、账号切换、旧观测晚到、提交失败、重启只回读，验证收藏事实语义等价。
- 请求层回归必须使用 Runtime 同款 RemoteAccess 代理：持久任务遇到连接失败只尝试一次，任务暂停在下次请求前生效，继续和退出仍保持现有安全语义；不需要连接真实账号。
- 在真实 HTTP 合成服务中短程重复混合读取和有限任务执行，观察最高在途数、checkout、WAL 增量、提交时间和 worker_error；不拿单次单查询或等待替身通过代替实际保存/提交路径。
- 现有日志测试只覆盖三失败步骤、110 个空操作和一个 skipped（`test_processing_log.py:15、51、67`）；现有大规模测试集中领取/进度/图库，并发处理器使用本地读取或等待替身，缺少大历史日志、断开后请求生命周期和收藏锁顺序，所以测试遗漏有具体边界。
