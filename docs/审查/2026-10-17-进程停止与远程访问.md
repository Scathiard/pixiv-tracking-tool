# 进程停止与远程访问调查

范围：用户报告外出使用 Tailscale 访问失败，随后反馈未主动关闭程序、手动启动时主页无响应、手机显示“仅允许当前局域网设备访问”。基线为 `main`、`0.2.0 / 20261017.1`，日常程序位于 `D:\PixivTracker`。本次只读诊断，没有修改实现、配置、数据库或系统设置，没有由调查工具重启程序。以下时间均为北京时间。

## 已确认的三个现象

### 1. 原进程在 Codex 更新时段突然停止

原运行 `eb7624219a7f` 的服务 PID 为 19060，启动父进程为 53728；[启用记录](证据/2026-10-17-读取与调度修订/enabled-launch.json)记载由工具里的 PowerShell ProcessStartInfo 启动。

- 19:33:16.377，诊断 seq298196：RSS 169,869,312 字节（162 MiB），事件循环间隔 141ms，日志线程存活，丢弃记录和探针错误均为 0。
- 19:33:16.562，seq298202：WAL 检查点完成，4676 帧处理完、busy=0、pending=0；seq298203 随后记录循环结束。
- 19:33:16.588，seq298204：最后一条是 140ms SQL 正常完成，error_type=null。末卷最后写入时间为 19:33:16.789。
- 19:33:16.752，Windows `Microsoft-Windows-AppXDeploymentServer/Operational` 事件 603：开始更新 Codex，参数包含 `ForceTargetApplicationShutdownOption`。事件 855 记录 `26.1007.2314.0` 更新为 `26.1013.4894.0`。
- 19:34:49，Windows 记录旧 Codex 桌面容器销毁、打包服务终止；19:34:50 启动新版。该时段 Application Hang 事件属于 Codex 包关联的 dllhost.exe，不是 PixivTracker 崩溃报告。

共检查旧运行两卷、298207 条可解析 JSON 记录和 890 次进程采样。RSS 峰值约 203.3 MiB；未见末尾内存暴涨、日志线程失败或正常退出标记。存在已处理的远端请求和浏览器错误，不能当作进程退出原因。

**判断：最符合证据的是 Codex 更新关闭关联进程时，连带结束了由工具启动的 PixivTracker。** 时间一致、启动关系和日志形态均支持；没有取得原进程退出码或点名 PID19060 的终止事件，故仍属于高度相关判断，不能宣称完全证明，也不能据此否认程序其他缺陷。

补充边界：新运行的父进程2060由 ChatGPT.exe 创建，但只读 GetPackageFullName 对2060和14680均返回无包身份（15700）。父子进程关系不能直接当作包身份或生命周期分组的证明；原进程已消失，当前结果也不能代替原进程的所属分组。尚未复现“更新开发工具带停日常服务”。

原始文件保留在 `D:\PixivTracker\data\diagnostic-20261017-190323-19060-eb7624219a7f-part0001.jsonl`、`part0002.jsonl` 和 `tracker.log`。没有清理这些证据。

### 2. 手动启动曾因任务恢复等待约 139 秒

新运行 `100da07ab4de`，服务 PID14680。普通日志记录：

- 21:11:37.804：task_recovery 开始。
- 21:13:56.634：task_recovery 完成，耗时 138829.7ms。
- 21:13:56.680：Web 服务启动完成；随后进度和图库均有成功请求。
- 21:15 左右，本机主页和状态接口返回 HTTP 200。

`app/src/web.py` 先绑定监听 socket，再等待 lifespan 中的 Runtime.start；后者在 `app/src/core/runtime.py` 等待 queue.recover 完成。因而“端口已经监听”不代表启动期间能返回网页。

进一步顺读本次启动记录：21:11:37.807 的 seq113 定义 SQL 指纹 `f9f9d2f33aaae2d3`，类型为 `SELECT operation_items`，调用点 `src/core/tasks.py:705:_recover_observed`。21:13:55.963（seq2654）仍在执行，21:13:56.631（seq2676）完成，耗时 **138828ms**、error_type=null；恢复结束（seq2693）实际恢复 item、operation、automatic_check 数量均为 0。该事务应用锁等待、取连接、BEGIN、末尾 flush/commit 均记录为 0ms；对应窗口没有远端请求事件。因此等待明确集中于本地任务恢复 SELECT，不能归咎于 Pixiv 登录。日志没有完整 SQL 或执行计划，尚未区分扫描规模、磁盘等待等更底层原因，不据此宣称需要改 schema。

本轮第一条 `/api/status` 探测在 4 秒外部检查窗口内未收到响应，之后就绪返回 200。没有改回程序内部超时或把初次失败删除。

### 3. Tailscale IPv4 被程序自己的局域网规则拦截

问题登记为 BUG-115。当前网卡和原函数只读复算结果：

| 项目 | 值 / 结果 |
| --- | --- |
| 电脑 Tailscale IPv4 | `100.94.235.37/32` |
| 手机 Tailscale IPv4 | `100.95.173.87`，被拒绝 |
| 电脑 Tailscale IPv6 | `fd7a:115c:a1e0::6b32:eb25`，被允许 |
| 手机 Tailscale IPv6 | `fd7a:115c:a1e0::6534:ad57`，被允许 |

`app/src/security.py` 的 NetworkPolicy.from_system 将活动网卡地址与掩码交给 from_interfaces；IPv4 /32 仅包含电脑自己的地址，没有纳入手机。RequestBoundaryMiddleware 在业务处理前返回 HTTP 403 和用户看到的提示。这与防火墙丢包、服务未监听、Pixiv 登录失败均不同。

Windows 的 psutil 此处没有返回 IPv6 掩码，现有规则回退为 /64，两台设备恰好落在相同范围。本机请求 `http://[fd7a:115c:a1e0::6b32:eb25]:1919/` 返回 HTTP 200（一次约 2ms），且原规则接受手机 IPv6；已请用户从手机验证，尚不能以电脑访问自己代替手机结果。此办法只利用当前已允许的地址，没有关闭校验。

后续手机反馈 IPv6 访问超时；其贴出的报错主机为 `[fd7a:115c:a1e0::6b32]`，缺少末段 `:eb25`，尚待核对地址栏原文，不能直接断言用户输入错误。21:37 再查同一服务 PID14680 仍监听 IPv4/IPv6，完整 IPv6 的本机访问返回200，手机 Tailscale 在线且探测往返59ms；这些检查仍不能证明手机浏览器到服务的 IPv6 HTTP 已连通。IPv6 临时办法保持未通过状态。

最终用户核对完整地址后回复“能访问了”，手机实际访问通过。当前可用入口为 `http://[fd7a:115c:a1e0::6b32:eb25]:1919/`；上述超时为先前验证过程记录。只读防火墙核对也发现针对该 Tailscale IPv4 和 IPv6 地址的现有入站允许规则，本次没有修改规则。BUG-115 的 IPv4 误拦、启动恢复慢以及原进程停止机制仍未修复或完全确证。

## 后续建议与边界

- 日常程序应从独立于 Codex 生命周期的入口启动，并验证更新开发工具不会带停日常程序；当前启动成功不等于这一点已验证。
- 为 Tailscale 明确建立访问支持，不能把单地址虚拟网卡当作普通局域网子网；保留已有 Host 和请求来源校验。
- 单独处理启动恢复的等待和可见反馈，保留恢复持久任务的语义；不以跳过恢复或删历史解决。
- 本次未实施修复、未重新打包；完整 IPv6 地址已通过用户手机验证，原进程确切终止机制仍需进一步证据。

参考：[Microsoft 的 ForceTargetApplicationShutdown 说明](https://learn.microsoft.com/en-us/powershell/module/appx/add-appxpackage?view=windowsserver2019-ps)说明该选项会强制关闭关联包的活动进程；[Tailscale 地址说明](https://tailscale.com/docs/reference/reserved-ip-addresses)列出其 IPv4 / IPv6 范围。文档用于解释机制，实际机器判断以本次日志和只读复算为准。
