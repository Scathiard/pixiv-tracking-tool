# 随机清单后台预计算研究

日期：2026-10-21。核对基线：`main / fc8d19ba237fd4efde75f3335dd9620e3fb2474a`，当前交付 `0.2.0 / 20261021.3`。本轮完成源码核对与一手资料研究，没有修改应用实现、图库结构或日常实例，没有追加真实全库查询。工作区已有 `app/tests/test_reading_query_scale.py` 改动及未跟踪文件保留。

用户明确的新要求：**允许首次准备耗时，但软件启动、图库更新后就应主动准备备用随机列表，不能等点随机才开始。** 用户随后批准本方案实施、定向验证和打包启用；以下研究阶段事实不等于实现验证。执行范围统一记入[功能路线图](../功能路线图.md) R-074，不另建执行队列。

## 结论与依据

当前应该改清单的读取、持有与刷新方式，保留现有线性洗牌。没有证据说明需要更复杂的伪随机排列算法，也不需要更换数据库或引入缓存服务器。

已有真实证据：16,676 件作品／53,008 页的清单请求耗时 43.178 秒，其中数据库读取 43.156 秒；有序 ID 段约 29.24 秒，版本／页数扫描约 13.92 秒。请求完成后的差额包含洗牌与会话发布，约十余毫秒，**不是独立的 shuffle 基准测试**。排队与连接池等待为 0。依据见[上轮诊断](2026-10-21-随机等待与连续切换诊断.md)及[读取摘要](证据/2026-10-21-随机等待与连续切换诊断/enabled-read-diagnostic.json)。本轮没有重跑这次测量，不能据此承诺新方案的实际耗时。

本轮源码核对确认：

- `ReadingSessions.create` 每次调用 `Library.reading_manifest`；两个浏览器创建阅读会话时没有共享的服务端基础清单。
- 浏览器的 `RandomReadingPreparation` 可以保留自己的准备，但软件无人打开网页时不会因此预热；`Runtime.start` 没有清单准备工作者。
- 常用范围的完整清单重复调用 480 件分页查询，再整段读取版本与页数。普通翻页需要分页；构建整份清单不应照搬这个循环。
- 现有 `read_model_meta.generation` 已区分成员／排序／筛选变化和普通任务进度，`read_model_dirty` 在同一写事务内捕获受影响身份，随后由 `maintain_projections` 消费。可以在这些既有事实之上补提交后通知，不必新建数据库表或触发器。
- 全局读控制的内存 generation 在每次成功写事务后都会增加，**不能拿它当随机清单的失效依据**，否则普通进度与资源状态写入也会反复刷新。

## 行业与社区采用的机制

| --- | --- | --- |
| [SQLite：覆盖索引与排序](https://www.sqlite.org/queryplanner.html#sorting_by_covering_index) | 查询需要的字段都在索引内时，可沿索引线性扫描，避免每行再查宽表。 | 完整基础清单按窄表／现有覆盖索引各读一遍，在内存拼接；不能只看 EXPLAIN 出现 index 就称性能问题已解决。 |
| [Navidrome：GetRandom 源码](https://raw.githubusercontent.com/navidrome/navidrome/master/persistence/mediafile_repository.go) | `GetRandom` 先选择随机 rowid，再读取选中的歌曲资料，避免让宽媒体记录参加随机排序。 | 借鉴编号与内容分离；它随机挑少量歌曲的场景，不能直接替代本项目完整、不重复遍历图库的合同。源码 master 为研究当日所见，未来可能变化。 |
| [Go：singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight#Group.Do) | 同 key 的并发调用共享一次正在执行的工作。 | 软件只有一个基础清单构建者，多浏览器复用准备结果，不因关闭某一个网页取消公共预热；借用机制，不增加 Go 依赖。 |
| [Caffeine：Refresh](https://github.com/ben-manes/caffeine/wiki/Refresh) | 支持异步刷新、进行中刷新去重，以及刷新失败保留旧值。其 `refreshAfterWrite` 默认由查询触发，并非到时自动刷新。 | 本项目必须额外由启动和成功提交主动触发，不能照搬查询时才刷新；旧值只供已固定的阅读会话使用，不静默冒充最新清单。 |
| [Linux：RCU 概述](https://docs.kernel.org/RCU/whatisRCU.html#rcu-overview) | 发布新版本后，旧读者可继续持有旧版本。 | 使用不可变清单和短锁整体替换即可，不移植内核机制；每个浏览器有自己的位置，不能共同消费一个可变队列。 |
| [CPython 3.12：random.shuffle](https://github.com/python/cpython/blob/3.12/Lib/random.py#L322-L328) | 倒序遍历并随机交换，工作量随成员数线性增长。 | 保留现有按作品洗牌，图库清单常驻后从内存补下一份随机顺序；多页作品仍整件连续。 |

以上是机制依据，**不是它们在本机机械盘上达到某个速度的证明**。基于本项目规模和日志，采用服务端预热、不可变快照、合并更新与内存洗牌，是本轮设计判断。

不采用全库宽查询 `ORDER BY RANDOM()` 作为修复：它仍需读取候选集合，且会引入排序工作；不能笼统说该写法在任何场景都错误。水塘抽样针对从流中选固定数量样本，不能替代完整无重复轮次，见 [Vitter 原论文](https://www.cs.umd.edu/~samir/498/vitter.pdf)。有限域伪随机置换可以避免保存某些排列，但仍要解决作品 ID 空洞、范围、版本和页数映射，不能消除这里的主要 I/O，见 [Black／Rogaway 原论文](https://web.cs.ucdavis.edu/~rogaway/papers/subset.htm)；当前没有证据证明增加这种复杂度有收益。

## 候选实现的关键边界

### 基础清单和备用顺序分开

基础清单只包含身份、默认版本、页数、可见性及已支持快速筛选／排序的必要字段；不带原图、简介或原始 JSON。启动后在后台读取一次，读取结束立即归还数据库连接。多次 SELECT 必须来自同一读快照，避免混入不同时间的版本与页数；SQLite WAL 支持读写并行，但长读仍会影响检查点推进。依据：[SQLite 隔离](https://www.sqlite.org/isolation.html)、[WAL 并发](https://www.sqlite.org/wal.html#concurrency)。

默认全图库范围提前保留一份完整随机排列及页位置索引，领取后从内存补下一份。每次阅览仍有独立种子／轮次和排除集合，不会因为共用基础清单就让两个设备相互抢位置。换排序、画师、类型或收藏等现有快速范围，可从同一精简快照产生对应成员；复杂文字／标签／日期组合保留现有正确查询，只复用有明确范围和版本的有限结果，不能声称所有任意组合都已在启动时计算。

复杂范围的缓存键必须包含完整筛选、`ceiling`、图库代次，以及“最近存入”的冻结参考时间 `as_of`；沿用现有 `_filter_key` 的时间语义。没有冻结参考时间的 recent 查询不跨请求复用，因为即使无人写库，时间流逝也会改变其成员。复杂范围只保留实际使用过的有限条目，不枚举全部筛选组合。

### 更新只补变化，不在每次下载后扫全库

在现有写事务成功提交后，传出其捕获的相关作品 ID 和图库代次；回滚不通知，普通任务计数、缩略图和文件发布状态不触发全量重建。新增、删除／隐藏、默认版本／页数变化、排序字段和收藏范围变化必须覆盖。

图库代次也会因画师名称和标签变化增长，不能把它等同于基础清单字段变化。通知要包含变更类别，不能只检查非空 `work` 身份：例如画师名称的 `card_artist` 事件虽不改变基础清单成员，却会影响文字筛选。核实不影响基础字段的事件可以复用成员、推进基础快照代次，同时使旧代次的复杂筛选缓存失效；不能丢掉空作品 ID 通知而让等待“追上代次”的新会话永久等待。

一个后台工作者合并短时间内的变更，只补读发生变化的作品并生成新快照／备用顺序。全量顺序扫描用于首次初始化或无法证明增量完整时的明确恢复路径，不作为普通更新默认路径。读取、排序、洗牌均不在提交回调或写锁里做。

初次扫描与后续补读都带代次。扫描期间的提交记录保留到被新快照覆盖；若补读看到比已收集通知更新的数据库代次，先补齐通知／重读相关集合，不能把不完整拼接标成最新。发布只替换完整版本；旧工作完成得晚不能覆盖新版本。

### 新会话取新清单，当前会话不被重排

当前阅读会话继续固定原成员、版本和随机轮次。新会话领取已追上其创建时图库代次的清单；后台新增不会让正在看的内容突然插队。已删除／隐藏项沿现有显式排除和不可用项处理路径跳过，不通过全局清空会话解决。

启动后立即预热指立即安排后台工作，**不让服务器等清单完成才接受网页请求**；FastAPI 官方生命周期文档说明 startup 完成前不会接收请求，因此预热不能作为阻塞启动步骤。依据：[FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/)。

冷启动尚未准备好、准备失败、切范围和用户取消要有对应状态；只取消该浏览器的等待，不终止共享构建。等待清单时不能占住前台数据库读取名额。后台构建限制为一个，遵守既有读控制与退出取消，退出前收回线程和连接。

目前 `POST /api/reading-sessions` 整体包在 `@local_read(frontend)` 中；必须把公共准备的等待移到数据库准入之外，不能只把内部查询换成条件变量等待。真正需要查询的工作仍走受控读取，不能通过移除装饰器把复杂筛选改成无界并行。

本轮先用进程内派生缓存，启动后主动重建；不新增缓存文件或真实库迁移。这样满足用户允许首次准备较长的要求。若以后要求刚启动立刻可随机，再单独讨论跨重启持久缓存及其来源核验，不能把过期文件当数据库事实。

## 验证和交付边界

只做针对性检查：无人打开网页时开始预热；多个浏览器只读一份基础清单；新增／隐藏／删除／版本与收藏变化后备用清单更新；任务进度不重建；扫描中提交不丢变更，回滚不生效；领取新清单不重排旧会话；关闭网页与软件退出的取消边界。

保留成员、顺序、页数和范围与现有实现的对照；验证预热完成后的会话创建不再扫描整库，用一次真实启动日志区分“初次准备耗时”和“用户切随机等待”，同时观察一个普通图库请求。真实盘结果出来前不写加速倍数；不追加全库长测，不把合成结果当真实盘性能。仍需最终 EXE 正常启用检查，普通详情和已交付连续流式交互保持。
