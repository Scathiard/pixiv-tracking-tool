# 阅览交互诊断与修订建议

日期：2026-10-19。基线：`main / 30f8613`，日常程序 `0.2.0 / 20261017.2`，诊断运行 `973f0fc8794d`。本轮只调查、隔离复现和提出方案，没有修改程序、替换 EXE、重启服务、修改真实图库或操作 Pixiv 账号。

## 结论

这次抓到的主要问题是交互流程相互阻塞：正常的收藏状态更新会使阅览定位失效；后台核对与用户点击共用禁用状态；详情在等图片时没有等待反馈。需要一起修复这三个衔接点，单改提示文案或按钮样式不足以解决。

最近会话的接口大多正常完成，不能把“用户点了没有反应”都解释成后端死机。也没有复现出在范围不变、目标图片及时就绪时独立的左右计算错误；真实失败发生在过期定位和媒体准备等路径。

## 已复现的实现问题

### BUG-117：正常后台变化使阅览定位失效

- `projection_maintenance.py:138–154` 用同一个全库代数记录作品、标签、画师名和收藏等变化；`library.py:474` 要求游标代数完全相等。
- 三件作品的真实 `ArchiveDatabase + Library` 复现中，查看全部作品并按最新排序时，给另一件作品新增一条“未收藏”记录，当前游标就失效；按作品 ID 恢复后，改变那件无关作品的收藏值，又失效。当前排序和范围实际无需因这次收藏变化而改变。
- `App.vue:203–245` 的普通切换继续带旧游标；只有专门的 `retryNavigation()` 走按作品 ID 重新定位。正常的下一件操作没有自动完成恢复并继续原方向。
- 在隔离回放中，单次手动恢复有效；后续又有写入时仍会再次失效。这解释了为什么一次恢复测试通过不代表日常“边更新边浏览”可用。

### BUG-118：后台核对挡住收藏意图，失败后还有等待出口缺失

- `state/bookmarks.ts:35,125–141,167–185` 将读状态、后台刷新和用户写入共用忙碌状态；`BookmarkButton.vue:43` 因此禁用按钮。后台核对时点击无法进入处理函数，也没有点击反馈。
- 仅取消前端禁用仍不够：`core/bookmarks.py:360–367` 对同作品已有的处理中操作直接复用，不区分“刷新事实”和“修改收藏”。真实服务合成复现中，刷新执行期间提交 `desired=true`，返回原刷新操作，最终仍为未收藏，远端写入调用次数为零。
- 写请求发生传输错误后，前端先等待恢复 GET，再把原错误交给界面；恢复 GET 不返回时，错误提示与红心都悬着。
- 操作查询连续九次失败后，轮询停止，但仍保留处理中与红心反馈。假时钟到 180 秒时已无定时器，按钮仍禁用；切回前台等动作可能重启核对，因此这是恢复状态缺口，不是已证明的数据库死锁。
- 三秒实心红心是 D-037 已确认的点击反馈要求，本轮不把它当作应删除的功能；临时反馈与最近确认的主站事实仍必须分开。

### BUG-119：详情切换被媒体准备挡住，却不展示等待状态

- `App.vue:209` 一开始切换就清空原错误；随后依次等待邻居、详情和 `prepareImage()`，完成前不提交新作品。
- `api.ts:187–214` 等图片加载和 `decode()`；图库／详情／流式没有呈现 App 级 `pending`，只有画师列表使用该状态。
- 直接执行现有 App 脚本、`LatestIntent`、`prepareImage` 的隔离回放中，只让目标图片解码等待，就得到“旧画面不动、错误为空、正在等待却不可见”；释放后立即完成切换。另一次输入会取消旧意图，用户无法判断上一下是否已经受理。
- 现场媒体事件支持“成功接口之后仍在等图／图失败”，不能进一步断言本次现场一定卡在 `decode()`；回放里的解码等待只是控制变量。

## 建议的 R-073 修订范围（待批准）

按用户操作流程完成一个修订包，先让操作可继续且反馈明确，再缩短已抓到的等待；不以更换技术栈或重做页面为前提。

| 顺序 | 用户得到的结果 | 实现边界 |
| --- | --- | --- |
| 1. 阅览恢复 | 后台有新作或收藏变化时，当前画面与操作继续可用；普通下一件不要求先找到“重新定位”按钮 | 保存当前作品 ID、页与本次方向；过期后自动按身份重新定位并继续该方向。单步优先使用已有邻居 ID，避免先额外拉一批图库卡片。定位与邻居解析尽量在同一只读快照完成，防止多个请求之间又过期 |
| 2. 缩小失效影响 | 无关作品的收藏刷新不再打断默认图库；新增内容仍由用户主动刷新接入 | 使用经当前筛选与可见性核验的身份／排序边界续读，保留本次范围上界；不直接忽略所有代数不匹配。真正隐藏、移出范围或排序改变时重新定位，必要时清楚说明并给就近位置或返回入口 |
| 3. 收藏意图独立 | 点击立即有既定反馈，后台核对不能吞掉点击；查询失败也能看出未确认并恢复核对 | 区分背景读取、用户目标和已确认事实；固定目标值、账号和请求 ID。同作品串行处理，刷新操作不得冒充收藏受理，仍保持写入去重与旧响应保护。错误通知不等恢复 GET；轮询停止后进入可恢复的待确认状态，结果不明时只核对、不盲目重复写入 |
| 4. 翻页与媒体反馈 | 按下后马上知道正在切换，图片慢或失败时仍可取消、重试或继续选择其他作品 | 保留旧图；分别呈现定位、准备图片、失败状态。可用预览先呈现、原图随后载入，只有实际展示就绪才切换；不把完整原件下载／额外解码作为不可见的门槛。相邻预取保持有限，连点不反复重启同一目标加载 |
| 5. 收藏受理等待 | 后台检查运行时，小操作不再长期堵在同一个大写入批次后 | 针对已确认的检查批次持写锁，缩短单批事务与投影工作量，在批次间让交互写入得到受理机会；保持每批原子性和恢复语义，不在持锁期间等待网络，不用增加线程数掩盖单写者争用 |

这是一份候选方案，不是开工授权。优先沿用当前 schema 与图库路径完成；若实际实现需要修改数据库触发器或新增持久结构，先另列具体结构候选。不会因本方案擅自恢复全局超时强杀；后台可以继续等待，但界面必须有反馈与取消／恢复出口。

界面继续保留只有心形的收藏按钮和既定点击动效，不恢复确认弹框；翻页等待放在现有底栏，不额外增加遮住图片的浮窗。

## 验证及边界

本轮只运行小型故障回放：收藏状态模块三条红灯场景、真实收藏服务意图冲突、三作品游标失效、详情切换脚本回放；另有现有收藏规则／反馈测试 15 项通过。未做全量、长测、真实收藏往返、EXE 或手机交互验收；完整 Runtime 构造尝试未及时完成，已停止，未记作成功。

后续若批准实施，重点只验四个完整过程：后台更新中继续翻页；后台收藏核对中点击并最终核实；图片慢／失败时连续左右操作与返回；网络失败后恢复核对且不重复写入。使用最终包做一次桌面和手机尺寸流程，再由用户在日常图库实用，不再用大量互不相连的单测代替体验。

可核对脚本、执行结果与复现限制见[证据说明](证据/2026-10-19-阅览交互诊断/README.md)。本次未证明整套程序均无后端超时，也未证明真实主站最终收藏结果；BUG-108、040／042 等已有问题不因此关闭。
