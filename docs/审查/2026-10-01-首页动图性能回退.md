# 首页动图性能回退

范围：BUG-086、R-010／R-011；基线 `main / e7bff6457b5e7c9d050b3b6dfcaba1c064a0eb4a`，旧内部包 20260930.4，候选公开版本 **0.2.0**、内部构建 **20261001.1**。不修改公开版本，不做图库结构转换。用户确认首页恢复播放但卡顿，未因此撤销动图预览需求。

## 结论和原因

此前把可见卡片接到完整 GIF，限制了数量，却没有限制每张动图的解码量。多张原尺寸、多帧 GIF 同时播放，持续消耗浏览器 CPU；滚动又需要绘制和切换图片，放大了成本。只判断“动画能播放、节点数量有界”不足以验证首页体验，本轮增加固定输入的性能对照。

真实库只读聚合：1,413 条 GIF 登记，最大 2,073,600 像素、42,874,937 字节；中位 317,200 像素、4,418,864 字节。不读取作品内容／令牌，不写真实库，不把这些聚合值视为实际浏览器性能测试。

80 件合成图库使用相同 1280×960、16 帧、800ms、3,517,985 字节 GIF；桌面固定 30 次真实滚轮，AB／BA 两轮。原尺寸与静态缩略图采用相同数据和接口；只缩小到 360×270、仍保留 16 帧时，静止 CPU 已下降约 75%～78%，滚动下降约 65%～72%。该控制支持解码／绘制成本的判断，未把界面轮询或数据库查询当作卡顿原因。

最终候选由生产生成器得到 360×270、8 帧、800ms、264,688 字节 WebP；使用真实 compact 接口，没有替换接口中的预览地址。比较数字如下，原始结果见[证据](证据/2026-10-01-首页动图性能回退/README.md)。

| 桌面同输入 | 旧包原尺寸动图 | 轻量缓存与滚动暂停 |
| --- | --- | --- |
| 静止 CPU，两轮 | 2.167／2.134 核当量 | 0.372／0.308 核当量 |
| 滚动 CPU，两轮 | 2.564／2.329 核当量 | 0.407／0.347 核当量 |
| 滚动 rAF 间隔 p95 | 23.6／47.0ms | 6／6ms |
| 超过 33ms 的间隔 | 12/470、58/450 | 1/520、0/513 |

CPU 是浏览器、渲染及 GPU 进程累计 CPU 秒除以实测时间，能够超过 1；不是整机百分比。下降约 83%～86% 只对应这组合成负载。rAF 是无头浏览器采样，不能据此宣称实体显示器帧率或所有设备均已顺畅。

## 实现和保护

- 卡片使用独立 `thumbnail / card-motion-v1` 派生物，最长边 360px、通常约 10fps、最多 120 帧，保留解码 GIF 的总播放时长；极短两帧循环保留两个状态及原时序。Pillow 的[动画 WebP 保存接口](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#webp)支持帧序列和播放时间；实际构建环境的 WebP 编码与浏览器播放另行验证。
- 顺序读取 GIF，不保存所有原尺寸帧；只保留缩小后的帧。卡片生成器限制输入帧数、累计输入像素和播放时长，帧边界可停止；发布前核对源指纹与版本，重启发布也拒绝过时来源。超过限制或转换失败保留原件与已有缓存。
- 复用既有 thumbnail 任务、本地处理通道、维护批次、资源互斥及安全发布；不增加端点、字段或 schema。只有已有缺项才分批生成，不在图库请求中同步转换，不联网补原包。缺 ZIP、主站不可访问的旧 GIF 仍可生成本地卡片缓存。
- compact 图库仅返回同源版本已核验的轻量动画；等待或失败期间显示现有静态缩略图，保留作品，不请求大 GIF 兜底。详情与流式继续显示完整 GIF。离屏和后台释放动画，滚动时暂停，停止 220ms 后恢复。
- 动画缓存使用内容版本地址，静态列表跳过动图查询；动图窗口批量读取，不能逐卡查询。首轮回归发现多一次 SQL，已修根因；5,000 件／2,000 页的原 SQL 上限未放宽。

源码入口：`GalleryView.vue`、`GalleryCardImage.vue`；`core/media.py`、`core/archive.py`、`core/maintenance.py`、`core/library.py`。原包补下载、来源确认、收藏和完整图库范围沿用既有规则。

## 验证状态

- 38 项前端测试、类型检查和正式前端构建通过；29 组动画交互和 7 组收藏／缩略图缓存浏览器检查通过，覆盖桌面、390／320px及 601 件连续浏览。
- 最终性能对照在桌面、390／320px均无页面错误和 CPU 预算超限。持续滚动采样的播放数均为 0，停止与返回后截图有明显实际帧变化；首页未请求原 GIF。桌面最多 40 张已挂载卡片，390／320px最多 14／16张，没有截断可浏览的总图库。
- 22 项卡片核心测试通过：GIF-only 离线生成、短循环、总时长、缺缓存维护、下载依赖、失败保留、源改变、删除阻止、重启发布及协作停止。修正后的状态／窗口定向 40 项通过，新增 1／60 件动图的批量读取检查。
- 首轮完整回归 355 通过、3 失败：两项旧测试仍要求首页加载大 GIF，一项确有 SQL 回退；原日志保留，修正契约且保留详情／流式及原件状态验收，没有降低窗口预算。最终完整回归 **359 项通过，177 条既有弃用警告**；失败与修正后的原始记录分别保存。
- 隔离源码冒烟 18 项通过：真实下载器仅连接本机合成 PNG／ZIP，发布 1280×960 原 GIF 与 360×270 卡片 WebP，详情仍用原 GIF；无法获取项跳过并保留已有内容。
- 独立 EXE **28 项浏览器、19 项隔离冒烟通过**；1440／390／320px 卡片实际播放 360×270 WebP，滚动暂停后恢复，详情读入 1280×960 原 GIF。筛选、来源清单、设置滚动、主题、画师和普通／流式入口回归通过。日常副本散列一致；实体手机、真实图库持续使用和用户体验待复验。

性能脚本一次生成同样本后硬链接注册 80 件；该实验未测量连续生成 80 件缓存的吞吐或峰值内存，实际队列生成／发布由核心测试和冒烟覆盖。首次启用时旧缓存需要后台补齐，补齐期间显示静态封面，不要求整库完成后才能浏览。未自动启动真实程序、触发账号写入、修改配置／令牌、删除旧包或公开发布。
