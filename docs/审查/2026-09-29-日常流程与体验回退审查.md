## 判断

这次重做改善了渲染和视觉，但没有守住日常操作的完整性。缺口集中在“找到入口 → 看懂对象 → 完成操作 → 得到可信反馈”的连续过程，主会话的产品设计与整体验收负责，不能让用户逐项补充本应保留的基本能力。

1. **功能保留清单停留在类别。** 路线图写了搜索添加、手动检查和筛选，验收却没有逐项映射旧控件与真实操作，新页面有相同栏目仍会丢功能。
2. **后台实现影响了产品表达。** 清点阶段承担了实际核验工作，却不进入主进度；结果按剩余执行项计数，做过全量核验仍可能显示“无需处理”。
3. **可靠性与日常检查没有分工。** 检查新作顺带刷新全部远端作品、清点已有本地内容和派生文件，让图库越大日常操作越重。
4. **界面验收重尺寸和技术边界，轻阅读空间与管理流程。** 既有触摸、导航、负载检查有价值，但“未横向溢出”没有证明手机信息层级、筛选与添加画师可用。
5. **视觉样稿与正式产品之间缺少完整流程验收。** R4 通过仅说明设计方向通过；主会话不应以构建、检查数量或小修版本交付替代整版日常体验评审。

## “校验存档”现在做什么

它是本地文件体检：核对登记的原件是否存在、非空、可解码，并检查动图原包与播放时序是否配对；会更新本地核验状态。它不负责检查画师新作，也不会自行补下载、删除原件或生成预览。

- 自动检查对属性未变的普通原件、GIF、缩略图可快速跳过；对已可用动图仍每轮读取时序 JSON 和 ZIP 目录比较帧名，不会因此逐帧解码或全包哈希。
- 手动 `verify` 对原件强制完整核验；GIF／缩略图仍走属性缓存，并不是所有媒体无差别重新解码。
- 100 件小图的隔离计划实验：首次自动检查完整核验 100 件，第二次 0 件，手动核验 100 件；两次自动检查均遍历作品。该实验不代表真实图库耗时。
- 还有结果遗漏：GIF／缩略图缺失可被写为 invalid，却未列入任务失败项；干净核验也没有代表核验成功的处理项。真实队列隔离执行确认：干净库和缺 GIF 两种情况均以 `empty／无需处理` 结束，后者 GIF 已被标为 invalid。登记 BUG-067，见[队列结果](证据/2026-09-29-日常流程审查/task-results-round.json)。
- 全量校验应移为设置里的明确手动维护任务；下载新文件时必要的校验、异常中断恢复继续保留。旧库 unknown 不等于文件坏了，也不能为提速直接伪装成 verified。

## 并行与反馈的产品边界

用户要的结果是：检查新作不会堵住下载，看图始终流畅，能看见正在做什么。建议在同一程序内分开检查、下载、转换／核验的工作通道，控制各自并发，共用限流和资产占用；数据库写入与文件发布保留一致性保护。不能直接多开完整 worker，因为旧规划过程自身也会修改文件状态，同一作品的删除、下载与转换存在依赖。

用户已选择**当前任务真实进度**：浮层上方显示任务名，下方一条有明确单位的进度，例如“检查画师 12/80”“下载页面 20/100”；其他并行任务只用一行小字说明。撤掉展开／收起和任务记录 UI；未知分母明确说明并展示已处理数量，不编造百分比。任务间切换必须同时更换名称和单位，不让同一名称下的百分比突然倒退。

内部仍须保存恢复信息和失败原因；普通通知自行消失，失败能在相关页面和设置日志入口找到，不要求常驻弹框。用于用户作决定的确认对话框与普通通知分开。
