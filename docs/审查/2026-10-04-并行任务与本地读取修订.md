## 已实现的修订

| 用户问题 | 实现与约束 |
| --- | --- |
| 后台维护拖住图库和设置 | 网页读取在占用线程、连接之前进入有界队列；阅览、后台和日志分别保留容量，写入使用独立容量 1 的连接池，仍由原单写锁串行提交。 |
| 页面已关闭，旧查询还在执行 | 单次读取共用截止时间，取消传递到 SQLite；连接归还前清理中断钩子和事务，不能让旧取消打断后来的请求。系统磁盘等待不承诺可强制中断。 |
| 日志越积越慢 | 近期概况只读必要字段，明细按现有索引和位置游标分窗；“有更早历史”与“明细尚未读全”分别表达，用户可继续读取。 |
| 反复打开设置和日志导致重叠或旧结果覆盖 | 共享读取按使用者计数，最后一个使用者离开才取消；页面卸载、重新打开和轮询均有明确生命周期，旧结果不能覆盖新页面。 |
| 多个设置请求重复统计并排队超时 | 设置和进度只共享正在执行的同范围 GET；成功提交后更新内存世代，账号／端口／登录变化另行隔离，失败提交不伪成功，不缓存已完成结果或合并写请求。 |
| 收藏读取与后台写入相互等待 | 内存锁只保护短暂状态，数据库工作在锁外执行；图库读取归还连接后再合成收藏快照，版本与账号仍在写事务内核对。 |
| 并行检查没有可靠接到客户端 | 正式 Runtime 代理显式传递任务上下文；请求暂缓时保存等待时间并让出检查者，未发出的请求不消耗网络重试。 |
| 重新登录与旧任务结果相互覆盖 | 凭据刷新按代际合并，运行实例和客户端共同标识请求来源；旧实例或没有来源记录的持久页先重新核对，不能直接写为当前账号事实。 |
| 每一步都统计整份阶段清单 | 首次进入阶段从步骤记录核对计数，随后将增量和步骤结论一同提交；每次重启重新核对，最终完成后释放内存标记。 |
| 已有就绪核对仍等全库清点 | 按每个操作在清点和就绪核对间轮转，保留同操作互斥与持久游标；某一侧冷却或没有可执行项时，另一侧继续。 |
| 冷却操作超过 64 项后，后来的任务排不到 | 操作候选用有界游标续扫；新请求及实际控制变化重新排队，重复提交不反复重置；暂停父图按代际只计算一次，父子关系在提交后发布。 |
| 只显示开始进度也单独占一次写入 | 开始进度和原子领取共用事务，提交成功后才认可阶段基线；空通道不借写连接，业务事实、结案及文件发布的持久记录不推迟。 |

检查者保留 1 个：本轮固定源码对照的第二个检查者没有改善整体延迟，写入等待 p95 增加。下载 2 个、本地重处理 1 个不变，检查与规划对同一操作互斥，就绪下载与预览可以接续；单次对照不作所有环境下两个检查者必然更慢的结论。

收藏仍以回读事实为准。审查另外发现并修复：已完成但回调尚未结束的操作占用容量，可能使新收藏意图被恢复流程抢走；现以未完成 Future 计算容量，并验证刚提交的写入不会变为只回读。读写压力下重试已开始的收藏操作，只回读，不重复发出写请求。

10 月 8 日进一步分解：3 件作品在旧调度中要先经过 8 个清点批次，才开始早已就绪的画师主页核对；修订后主页核对在第 2 次调度开始，作品核对／补齐在第 5 次开始，此时清点尚未完成，全部 8 批仍会继续。另以正常两帧 ZIP 和真实处理器比较，同一步由 5 次提交（4 次有数据修改）降为 4 次提交（3 次有修改），只合并开始显示；没有据此推断整体速度提升比例。

测试输入复审发现，旧大型夹具虽标记 `0003_revisions`，最初未创建作品版本和绑定，且动图时序错误地写成裸数组。旧文件和失败结果完整保留，仍可用于异常输入诊断；后续标准夹具按正式助手建立当前版本／绑定，时序改为正式 `{"frames": ...}` 结构，并保证合成主站回读不会无意义地产生新版本。1,000 件小型输入自检通过，正式大规模仍保留 15,000 件、150,512 历史步骤、四态宽 JSON、15 份缺原件与 60 份缺静态预览，后续不将两种输入的结果直接充作性能 A/B。

计时仪器改为保留各类最慢分段及慢 SQL 的起止时刻，分位样本覆盖整个运行时段，并记录 CPU／内存／WAL；不能因只保存前段样本而遗漏后段长尾。5.689 秒提交的准确机制仍未确认，未修改 SQLite 的同步强度或检查点阈值。旧有限重试测试另已修正合成输入：明确模拟已发出并收到 HTTP 429 的请求，原重试上限不变，未发送冷却仍不消耗次数。

规范图库短测进一步定位：同一波 7 个设置请求独立重复统计，4 份统计各用 1.890～2.673 秒并占满前台容量，另外 3 份排队 3.523～3.944 秒后预算不足；不是已证明单次静止统计超过预算。补做单份读取对照，并验证只在途共享及提交后世代边界。此轮提交最长 4.212 秒，其间两个简单读取也等待约 3.793 秒，机制仍待归因，不能直接归因于检查点或磁盘刷写；请求之后采样到的前台活动峰值 0 也不能证明没有并发，后续补事件峰值记录。

同一规范库的静止副本中，4 次完整设置响应为 0.800／0.360／0.370／0.356 秒，统计约 0.326～0.342 秒；未清除系统文件缓存，不能称为冷盘测试。后续仪器在真实受理计数变动与连接借还时记录峰值，并将定时采样另列；小型自检捕获 4 活动、1 等待和 4 个读连接，全部归零且封装恢复，日志锁等待不会移动测量起止时刻。

独立小反例另确认：64 个较早的冷却手动操作会让第 65 个已就绪任务连续 32 次调度仍无机会，减为 63 个旧操作时正常结案；原因是操作候选窗口只有前 64 项、未继续扫描。暂停父图也在一轮中按每节点重复复制全图，4／8／16／32／64 节点分别复制 16／64／256／1024／4096 项；已改为有界续扫及按代际单次快照；暖暂停检查不复制图、不借数据库，回滚不发布父边、重启能恢复已完成中间节点的继承关系。无变化去重不重置窗口，双检查者仍互斥；不把此现象直接当作整库维护长提交的原因。

最新短测的 2.506 秒受理已分段归因：其中 2.354 秒在等写锁，持锁者正在执行 2.811 秒的数据库提交；未记录该事务完整 DML，因此不能推断具体业务步骤。设置的 21 个 HTTP 均成功，慢语句记录每波 1 份统计，专项屏障另证明 7 请求只执行 1 次统计。

对关闭后的合成副本，固定 64×32 条清单写入流比较自动检查点：1000 页阈值的四次长提交均对应越界，最长 6.627 秒；只作因果对照的关闭自动检查点版本最长提交 0.324 秒，但末尾手动检查点仍耗 5.191 秒、WAL 达 19.15 MB，不作为产品方案。随后将复制文件预先单独同步并反转顺序：256 页最长提交／写锁等待 1.616 秒，1000 页 2.885 秒；两组含末尾检查点总耗时为 29.845／18.099 秒，256 的 p95 更差、吞吐约下降 39%。此前未预同步的 128 页尖峰保留为受干扰结果，不据此选择参数。

实验候选曾将业务写连接设为 256 页自动 PASSIVE 检查点并显式保持 FULL；优先限制一次合并占用保存通道的时间，代价是更频繁的合并。没有新增写线程、连接、结构或迁移；阈值不是 WAL 硬上限，也不能保证任意磁盘等待小于 2 秒。四组 SQL、实际变更量及重开数据哈希相同，完整性检查通过；这仅证明合成写流机制，正式大库、整体耗时和持续验收仍须复测。随后因吞吐代价及用户提出的机械盘问题，256 页策略已撤回，生产继续沿用默认自动检查点与 FULL；实验源码、专属红绿结果原位保留，通用快照／回滚回归按实际检查点周期验证。依据为 SQLite 的[检查点与提交说明](https://sqlite.org/wal.html#performance_considerations)。
